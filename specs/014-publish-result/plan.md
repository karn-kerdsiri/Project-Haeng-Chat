# Plan: UC-14 เผยแพร่ผลการตรวจสอบคุณสมบัติ

## 1. สรุปแนวทาง
- ฟีเจอร์นี้เกี่ยวข้องกับกระบวนการ “เผยแพร่ผล” หลังจากผลการตรวจสอบได้รับการยืนยันแล้ว โดยเจ้าหน้าที่จะตรวจสอบความพร้อมก่อนเผยแพร่ แล้วเปลี่ยนสถานะเป็น “เผยแพร่” และเรียก UC-17 เพื่อแจ้งผลให้ผู้มีสิทธิ์ทราบ
- การออกแบบจะยึด spec.md เป็นแหล่งความจริงเดียว และคง Open Questions OQ-PUB-01 ถึง OQ-PUB-06 ไว้โดยไม่เดาตอบแทนจนกว่าทีมจะตอบชัดเจน
- แนวทางหลักประกอบด้วย 4 ส่วน: ตรวจความพร้อมก่อนเผยแพร่, แสดงรายการที่พร้อมเผยแพร่, ปฏิบัติการเผยแพร่พร้อมบันทึกประวัติ, และเรียก UC-17 เพื่อแจ้งเตือนแบบรวมศูนย์ตาม constraints ที่ระบุ

## 2. ข้อจำกัดและกฎที่ต้องปฏิบัติตาม

| ID | ข้อความหลัก | การใช้ในแผน |
|---|---|---|
| IF-AUTH-01 | ทุก request ต้องมี session ที่ยืนยันตัวตนกับระบบมหาวิทยาลัย มิฉะนั้น HTTP 401 | ใช้สำหรับทุก endpoint ของ UC-14 |
| IF-WEB-01 | หน้าจอทำงานบนเบราว์เซอร์ปกติ โดยไม่ต้องติดตั้งโปรแกรมเพิ่ม | ใช้สำหรับ UI รายการและรายละเอียดผล |
| IF-TECH-01 | ส่วนหน้าจอใช้ React และสถานะการเผยแพร่เก็บใน PostgreSQL | ใช้เป็นสถาปัตยกรรมรากฐานของแผน |
| IF-AUDIT-01 | ทุกการเผยแพร่ต้องบันทึกประวัติพร้อมผู้ดำเนินการและเวลา | ใช้ใน action publish และ audit history |
| IF-NOTIFY-01 | แจ้งผลผ่าน UC-17 เท่านั้น ไม่สร้างกลไกแยก | ใช้เป็น integration contract กับ UC-17 |
| CON-PUB-01 | เผยแพร่ได้เฉพาะผลที่ผ่านการตรวจสอบและยืนยันครบถ้วนตามเงื่อนไข | ใช้เป็นเงื่อนไขระดับ service |
| CON-PUB-02 | เฉพาะผู้ใช้บทบาทเจ้าหน้าที่ที่มีสิทธิ์เผยแพร่จึงจะทำได้ | ใช้ใน authz middleware |
| CON-PUB-03 | เมื่อเผยแพร่ไม่สำเร็จ สถานะต้องไม่เปลี่ยน | ใช้เป็น rollback rule |

## 3. โมเดลข้อมูลและบริการหลัก

### 3.1 โมเดลข้อมูล
- PublishCandidate
  - request_id, student_id, student_name, result_summary, status, confirmed_flag, ready_for_publish_flag
  - สร้างจากข้อมูลที่ได้จาก UC-13 และ UC-16 เพื่อใช้ให้เจ้าหน้าที่ตรวจทานก่อนเผยแพร่
- PublishRecord
  - request_id, published_by, published_at, previous_status, new_status, result_snapshot
  - ใช้เก็บประวัติการเผยแพร่ตาม DR-PUB-04 และ IF-AUDIT-01
- NotificationTrigger
  - publish_record_id, notification_type, triggered_by_uc, sent_at
  - ใช้สำหรับการเรียก UC-17 ที่ต้องทำผ่าน IF-NOTIFY-01

### 3.2 บริการหลัก
- PublishGateService
  - ตรวจความครบถ้วนตาม DR-PUB-02 และ CON-PUB-01 ก่อนให้รายการปรากฏใน list ที่พร้อมเผยแพร่
- PublishListService
  - ดึงรายการที่พร้อมเผยแพร่ตาม DR-PUB-01 เพื่อให้เจ้าหน้าที่ตรวจทาน
- PublishActionService
  - ทำการเปลี่ยนสถานะเป็น “เผยแพร่” ตาม DR-PUB-03 พร้อม transaction และ rollback เมื่อไม่สำเร็จ
- NotificationBridge
  - เรียก UC-17 หลังการ publish สำเร็จ โดยไม่สร้าง notification logic แยกในฟีเจอร์นี้

## 4. API / UI ที่จะออกแบบ

| รายการ | ขอบเขต | รองรับ ID |
|---|---|---|
| GET /publish/requests | แสดงรายการผลที่พร้อมเผยแพร่ให้เจ้าหน้าที่ตรวจทาน | FR-PUB-01, FR-PUB-02 |
| GET /publish/requests/{id} | แสดงรายละเอียดผลพร้อมข้อมูลยืนยันและผลตรวจสอบ | FR-PUB-02 |
| POST /publish/requests/{id}/publish | ตรวจสิทธิ์และความพร้อม แล้วเปลี่ยนสถานะเป็นเผยแพร่ | FR-PUB-03, CON-PUB-01, CON-PUB-02, CON-PUB-03 |
| POST /publish/requests/{id}/notify | เรียก UC-17 สำหรับแจ้งผล | FR-PUB-04, IF-NOTIFY-01 |
| GET /publish/history | แสดงประวัติการเผยแพร่พร้อมผู้ดำเนินการและเวลา | FR-PUB-09, IF-AUDIT-01 |
| UI: PublishListPage | หน้าแสดงรายการพร้อมเผยแพร่ | FR-PUB-01, FR-PUB-02 |
| UI: PublishDetailPage | หน้ารายละเอียดผล พร้อมปุ่มเผยแพร่/ย้อนกลับไปแก้ไข | FR-PUB-03, FR-PUB-05, FR-PUB-06 |

## 5. ข้อกำหนดที่ยังไม่ได้ตอบ (ต้องคงไว้)
- OQ-PUB-01: รายการที่พร้อมเผยแพร่ต้องแสดงฟิลด์ใดบ้าง และควรจัดกลุ่มตามกลุ่มอาจารย์หรือภาคการศึกษาหรือไม่
- OQ-PUB-02: นอกจากสถานะยืนยันแล้ว ยังมีเงื่อนไขอื่นที่ต้องครบก่อนเผยแพร่หรือไม่ เช่น ต้องยืนยันครบทุกคนในรอบนั้นหรือไม่
- OQ-PUB-03: การเผยแพร่เป็นรายคน รายกลุ่ม หรือทั้งรอบพร้อมกัน และชื่อสถานะหลังเผยแพร่ใช้คำว่าอะไร
- OQ-PUB-04: ก่อนเผยแพร่ นักศึกษาสามารถเห็นผลการตรวจสอบของตนเองได้หรือไม่ และถ้าเห็นได้ ต้องแสดงข้อมูลอะไร
- OQ-PUB-05: หลังเผยแพร่แล้วสามารถยกเลิกหรือเผยแพร่ซ้ำได้หรือไม่ ใครมีสิทธิ์ และต้องแจ้งเตือนผู้รับซ้ำหรือไม่
- OQ-PUB-06: ผู้มีสิทธิ์เข้าดูผลที่เผยแพร่มีใครบ้าง

## 6. ลำดับการทำงาน
1. ตรวจสอบข้อมูลที่สามารถใช้เป็น “พร้อมเผยแพร่” ตาม FR-PUB-01, DR-PUB-02 และ CON-PUB-01 โดยคง OQ-PUB-01 และ OQ-PUB-02 ไว้เป็นบล็อกเกอร์ที่ยังไม่ได้ตอบ
2. ออกแบบ API และ session/role guard สำหรับเจ้าหน้าที่เผยแพร่ โดยยึด IF-AUTH-01, CON-PUB-02 และ FR-PUB-10
3. สร้าง service สำหรับการเผยแพร่และบันทึกประวัติ พร้อมตรวจ transaction/rollback ตาม CON-PUB-03 และ IF-AUDIT-01
4. สร้าง integration กับ UC-17 สำหรับการแจ้งผลหลัง publish สำเร็จ โดยใช้ contract ตาม IF-NOTIFY-01
5. ออกแบบ UI รายการพร้อมเผยแพร่และหน้า detail พร้อมข้อความภาษาไทย และรองรับหน้า mobile ตาม IF-WEB-01
6. วางแผนทดสอบ end-to-end สำหรับ AC-PUB-01 ถึง AC-PUB-08 โดยให้กรณี error/forbidden/history ถูกตรวจสอบชัดเจน

## 7. แผนทดสอบจาก Acceptance Criteria
- AC-PUB-01: ทดสอบการเผยแพร่สำเร็จเปลี่ยนสถานะและเปิดให้ผู้มีสิทธิ์เข้าดูผล
- AC-PUB-02: ทดสอบการเรียก UC-17 หลัง publish สำเร็จ
- AC-PUB-03: ทดสอบการปฏิเสธเมื่อข้อมูลยังไม่พร้อม/ยังไม่ผ่านเงื่อนไข
- AC-PUB-04: ทดสอบการย้อนกลับไปแก้ไข/ยืนยันใหม่ผ่าน UC-13 เมื่อพบข้อมูลผิดพลาด
- AC-PUB-05: ทดสอบกรณี publish ล้มเหลวแล้วสถานะคงเดิม
- AC-PUB-06: ทดสอบการปฏิเสธ HTTP 403 สำหรับผู้ใช้ที่ไม่มีสิทธิ์
- AC-PUB-07: ทดสอบบันทึกประวัติผู้ดำเนินการ เวลา และรายการที่เผยแพร่
- AC-PUB-08: ทดสอบว่า result ที่ยังไม่ได้เผยแพร่ไม่แสดงต่อผู้ที่ไม่มีสิทธิ์

## 8. ข้อสรุปทางออก
- Plan นี้จะไม่ตั้งสมมติฐานเกินจาก spec ที่มีอยู่และจะไม่สร้าง logic ที่ต้องอาศัยคำตอบ Open Questions ที่ยังไม่ได้รับ
- พื้นที่ที่ยังไม่ชัดเจนจะถูกจัดให้เป็น blocker ในกระบวนการพัฒนา และแก้ไขเฉพาะเมื่อทีมตอบคำถามดังกล่าวแล้วเท่านั้น
