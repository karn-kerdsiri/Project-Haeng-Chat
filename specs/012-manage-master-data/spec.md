# Feature: จัดการข้อมูลรายวิชา อาจารย์ และเงื่อนไขการผ่าน (Manage Master Data)
Spec ID: SPEC-MST-012 | Source: Use Case Specification UC-12 จัดการข้อมูลรายวิชา อาจารย์ และเงื่อนไขการผ่าน + รายการความต้องการของทีม ข้อ 4, ข้อ 14 | Use case: UC-12
Owner: ทีม B | Status: Draft v2 | Updated: 2569-11-13

## Goal
เจ้าหน้าที่เพิ่ม แก้ไข ลบ หรือปรับปรุงข้อมูลรายวิชา รายชื่ออาจารย์ เงื่อนไขการผ่าน และโควต้าอาจารย์ได้
เพื่อให้ระบบใช้ข้อมูลที่เป็นปัจจุบันในการตรวจสอบคุณสมบัติ

## Scope
### In scope
- IN-MST-01 แสดงรายการข้อมูลรายวิชา อาจารย์ เงื่อนไขการผ่าน และโควต้าอาจารย์   <- UC-12 ขั้น 1 + ข้อ 4
- IN-MST-02 เพิ่ม แก้ไข หรือลบข้อมูลแต่ละประเภท                            <- UC-12 ขั้น 2-3
- IN-MST-03 ตรวจสอบข้อมูลก่อนบันทึก รวมถึงกรณีข้อมูลซ้ำและข้อมูลไม่ครบ        <- UC-12 ขั้น 4, alt 1-2
- IN-MST-04 บันทึกและแสดงผลสำเร็จ                                        <- UC-12 ขั้น 5-6
- IN-MST-05 ป้องกันการลบข้อมูลที่ถูกใช้งานอยู่ และแจ้งผลกระทบ                 <- UC-12 alt 3
### Out of scope
- OUT-MST-01 การตรวจสอบเงื่อนไขเบื้องต้นและการคำนวณผล - เป็นของ UC-07 และ UC-16 ซึ่งอ่านข้อมูลจากฟีเจอร์นี้
- OUT-MST-02 การจัดทำตารางเวลาประจำเทอม - เป็นของ UC-15
- OUT-MST-03 การตรวจสอบและยืนยันข้อมูลที่นักศึกษาส่งมา - เป็นของ UC-13
- OUT-MST-04 การสร้างบัญชีผู้ใช้ของอาจารย์ - ใช้บัญชีเดียวกับระบบของมหาวิทยาลัยตามข้อ 12
- OUT-MST-05 การอัปโหลดและปรับปรุงเอกสารให้นักศึกษาดาวน์โหลดตามข้อ 5 - UC-12 ไม่ครอบคลุม (ดู ASM-MST-04)

## Constraints
- IF-AUTH-01 ทุก request ของฟีเจอร์นี้ต้องมี session ที่ยืนยันตัวตนด้วยบัญชีเดียวกับระบบของมหาวิทยาลัย มิฉะนั้นตอบ HTTP 401   <- ข้อ 12
- IF-WEB-01 ทุกหน้าจอของฟีเจอร์นี้ต้องทำงานบนเบราว์เซอร์โดยไม่ต้องติดตั้งโปรแกรมเพิ่ม   <- ข้อ 13
- IF-TECH-01 ส่วนหน้าจอพัฒนาด้วย React และข้อมูลพื้นฐานเก็บในฐานข้อมูล PostgreSQL   <- ข้อ 19
- IF-AUDIT-01 ทุกการเพิ่ม แก้ไข และลบข้อมูลต้องบันทึกประวัติพร้อมผู้ดำเนินการและเวลา   <- ข้อ 8
- DOM-QUOTA-01 อาจารย์หนึ่งคนรับนักศึกษาได้ไม่เกินโควต้าที่คณะกำหนดในแต่ละภาคการศึกษา   <- ข้อ 14
- DOM-GRADE-01 เงื่อนไขการผ่านต้องอ้างอิงเกรดตามระบบเกรดของมหาวิทยาลัย และต้องไม่นับรายวิชาที่ผลไม่สมบูรณ์ว่าผ่าน   <- ข้อ 16
- CON-MST-01 เฉพาะผู้ใช้บทบาทเจ้าหน้าที่ที่มีสิทธิ์จัดการข้อมูลจึงจะเพิ่ม แก้ไข หรือลบได้   <- UC-12 Precondition
- CON-MST-02 ห้ามลบข้อมูลที่ถูกอ้างอิงใช้งานอยู่   <- UC-12 alt 3

## Data Rules
- DR-MST-01 ประเภทข้อมูลที่จัดการในฟีเจอร์นี้: รายวิชา, รายชื่ออาจารย์, เงื่อนไขการผ่าน, โควต้าอาจารย์   <- ข้อ 4
- DR-MST-02 ฟิลด์บังคับของรายวิชา: รหัสวิชาและชื่อวิชา (ดู ASM-MST-05)
- DR-MST-03 ฟิลด์บังคับของอาจารย์: ชื่ออาจารย์ และข้อมูลที่ใช้เชื่อมโยงบัญชีมหาวิทยาลัย (ดู ASM-MST-05)
- DR-MST-04 ฟิลด์บังคับของโควต้า: อาจารย์ ภาคการศึกษา และจำนวนนักศึกษาสูงสุด   <- ข้อ 14
- DR-MST-05 ฟิลด์บังคับของเงื่อนไขการผ่าน: ชื่อเงื่อนไข เกณฑ์ที่ใช้ตัดสิน และสถานะใช้งาน (ดู ASM-MST-06)
- DR-MST-06 นิยามข้อมูลซ้ำ: รายวิชาที่มีรหัสวิชาเดียวกัน, อาจารย์ที่ผูกกับบัญชีเดียวกัน, โควต้าของอาจารย์คนเดียวกันในภาคการศึกษาเดียวกัน   <- UC-12 alt 1
- DR-MST-07 จำนวนนักศึกษาสูงสุดในโควต้าต้องเป็นจำนวนเต็มไม่น้อยกว่า 0   <- ข้อ 14

## Requirements
- FR-MST-01 ระบบต้องแสดงรายการข้อมูลแต่ละประเภทตาม DR-MST-01   <- UC-12 ขั้น 1
- FR-MST-02 ระบบต้องให้เจ้าหน้าที่เลือกเพิ่ม แก้ไข หรือลบข้อมูล   <- UC-12 ขั้น 2
- FR-MST-03 ระบบต้องให้กรอกหรือปรับปรุงข้อมูลตาม DR-MST-02 ถึง DR-MST-05   <- UC-12 ขั้น 3
- FR-MST-04 เมื่อข้อมูลไม่ครบหรือผิดรูปแบบ ระบบต้องไม่บันทึก และแจ้งช่องที่ต้องแก้ไขเป็นรายช่อง   <- UC-12 ขั้น 4, alt 2 + ข้อ 10
- FR-MST-05 เมื่อพบข้อมูลซ้ำตาม DR-MST-06 ระบบต้องแจ้งเตือนและไม่สร้างข้อมูลซ้ำ   <- UC-12 alt 1
- FR-MST-06 เมื่อผ่านการตรวจสอบ ระบบต้องบันทึกข้อมูลและแสดงผลสำเร็จ   <- UC-12 ขั้น 5-6
- FR-MST-07 เมื่อเจ้าหน้าที่พยายามลบข้อมูลที่ถูกใช้งานอยู่ ระบบต้องป้องกันการลบ และแจ้งว่าข้อมูลนั้นถูกใช้ที่ใด   <- UC-12 alt 3, CON-MST-02
- FR-MST-08 หากบันทึกไม่สำเร็จ ระบบต้องแจ้งข้อผิดพลาด และไม่บันทึกข้อมูลบางส่วน   <- UC-12 Exception
- FR-MST-09 ข้อมูลที่บันทึกต้องพร้อมให้ UC-06, UC-07 และ UC-16 นำไปใช้ทันทีหลังบันทึกสำเร็จ   <- UC-12 Postcondition
- FR-MST-10 ระบบต้องบันทึกประวัติการเพิ่ม แก้ไข และลบพร้อมผู้ดำเนินการตาม IF-AUDIT-01   <- ข้อ 8
- FR-MST-11 ระบบต้องปฏิเสธการจัดการข้อมูลโดยผู้ใช้ที่ไม่มีสิทธิ์ด้วย HTTP 403   <- CON-MST-01
- FR-MST-12 ระบบต้องให้กำหนดโควต้าอาจารย์แยกตามภาคการศึกษาตาม DOM-QUOTA-01 และ DR-MST-04   <- ข้อ 14

## Quality Requirements
- NFR-MST-01 [Security] ระบบต้องตัดการเชื่อมต่อของบัญชีผู้ใช้อัตโนมัติ เมื่อไม่มีการใช้งานต่อเนื่องเกิน 30 นาที   <- ข้อ 9
- NFR-MST-02 [Security] เฉพาะบทบาทเจ้าหน้าที่ที่มีสิทธิ์จัดการข้อมูลจึงจะเรียก API เพิ่ม/แก้ไข/ลบได้   <- UC-12 NFR (Security)
- NFR-MST-03 [Data Integrity] การแก้ไขข้อมูลที่ถูกใช้งานอยู่ต้องไม่ทำให้ข้อมูลคำร้องที่อ้างอิงอยู่เสียความถูกต้อง   <- UC-12 NFR (Data Integrity) (ดู ASM-MST-07)
- NFR-MST-04 [Auditability] ประวัติการเปลี่ยนแปลงข้อมูลพื้นฐานต้องเก็บไว้ไม่น้อยกว่า 1 ปี และระบุผู้ดำเนินการได้   <- UC-12 NFR (Auditability) + ข้อ 8 (ระยะเวลา 1 ปีเป็นค่าที่เสนอไว้ ดู ASM-MST-01)
- NFR-MST-05 [Usability] ข้อความแจ้งข้อผิดพลาดต้องเป็นภาษาไทย และระบุช่องที่ต้องแก้ไข   <- ข้อ 10
- NFR-MST-06 [Usability] ทุกหน้าจอของฟีเจอร์นี้ต้องใช้งานได้บนจอโทรศัพท์มือถือ โดยไม่มีการเลื่อนแนวนอนที่ความกว้างจอตั้งแต่ 360 px   <- ข้อ 11 (ค่า 360 px เป็นค่าที่เสนอไว้ ดู ASM-MST-01)

## Acceptance Criteria
- [ ] AC-MST-01 (FR-MST-06, FR-MST-09)
      Given เจ้าหน้าที่มีสิทธิ์จัดการข้อมูล
      When  บันทึกข้อมูลรายวิชาที่ถูกต้องครบถ้วน
      Then  ระบบบันทึกสำเร็จ และข้อมูลนั้นถูกนำไปใช้ในการตรวจสอบได้
- [ ] AC-MST-02 (FR-MST-05, DR-MST-06)
      Given มีรายวิชารหัส X อยู่แล้ว
      When  เพิ่มรายวิชารหัส X อีกครั้ง
      Then  ระบบแจ้งเตือนข้อมูลซ้ำ และไม่สร้างข้อมูลซ้ำ
- [ ] AC-MST-03 (FR-MST-04, NFR-MST-05)
      Given กรอกข้อมูลไม่ครบตาม DR-MST-02
      When  กดบันทึก
      Then  ระบบไม่บันทึก และแสดงข้อความภาษาไทยที่ช่องที่ต้องแก้ไข
- [ ] AC-MST-04 (FR-MST-07, CON-MST-02)
      Given รายวิชา X ถูกอ้างอิงอยู่ในคำร้องของนักศึกษา
      When  เจ้าหน้าที่พยายามลบรายวิชา X
      Then  ระบบไม่ลบ และแจ้งว่ารายวิชานั้นถูกใช้งานอยู่ที่ใด
- [ ] AC-MST-05 (FR-MST-12, DOM-QUOTA-01, DR-MST-04)
      Given กำหนดโควต้าของอาจารย์ A ในภาคการศึกษาปัจจุบันเป็น 10 คน
      When  บันทึกโควต้า
      Then  ระบบบันทึกโควต้าแยกตามภาคการศึกษา และ UC-06 ใช้ค่านี้จำกัดการเลือกกลุ่ม
- [ ] AC-MST-06 (FR-MST-11, NFR-MST-02)
      Given ผู้ใช้ที่ไม่ใช่เจ้าหน้าที่ที่มีสิทธิ์
      When  เรียก API เพิ่มหรือลบข้อมูลพื้นฐาน
      Then  ระบบตอบ HTTP 403 และข้อมูลไม่เปลี่ยนแปลง
- [ ] AC-MST-07 (FR-MST-10, IF-AUDIT-01, NFR-MST-04)
      Given เจ้าหน้าที่แก้ไขเงื่อนไขการผ่าน 1 ครั้ง
      When  บันทึกสำเร็จ
      Then  มีประวัติ 1 รายการที่ระบุผู้ดำเนินการ เวลา และค่าก่อน/หลัง
- [ ] AC-MST-08 (FR-MST-08)
      Given ฐานข้อมูลไม่พร้อมใช้งานขณะบันทึก
      When  กดบันทึก
      Then  ระบบแจ้งข้อผิดพลาด และไม่มีข้อมูลบางส่วนถูกสร้าง
- [ ] AC-MST-09 (DR-MST-07)
      Given กรอกจำนวนนักศึกษาสูงสุดเป็นค่าติดลบ
      When  กดบันทึกโควต้า
      Then  ระบบไม่บันทึก และแจ้งรูปแบบที่ถูกต้อง

## Assumptions & Open Questions
- ASM-MST-01 UC-12 ระบุ NFR เป็นหมวด (Security, Data Integrity, Auditability) ค่าตัวเลขใน NFR-MST-04 และ NFR-MST-06 จึงเป็นค่าที่เสนอไว้เพื่อให้ทดสอบได้
- ASM-MST-02 ข้อ 19 ระบุ React + PostgreSQL spec นี้จึงยึดข้อ 19 ซึ่งต่างจาก plan.md ของ specs/001-Enter-educational-information ที่ใช้ Supabase ทีมต้องตัดสินและปรับ 001 ให้ตรงกัน
- ASM-MST-03 ข้อ 4 ระบุโควต้าอาจารย์เป็นข้อมูลที่เจ้าหน้าที่จัดการ spec นี้จึงรวมโควต้าไว้ในขอบเขตของ UC-12 ซึ่ง UC-12 เขียนชื่อไว้เพียง "รายวิชา อาจารย์ และเงื่อนไขการผ่าน"
- ASM-MST-04 การอัปโหลดและปรับปรุงเอกสารให้นักศึกษาดาวน์โหลดตามข้อ 5 อยู่นอกขอบเขตของ UC-12 ตาม OUT-MST-05
- ASM-MST-05 ฟิลด์หลักของรายวิชาประกอบด้วย รหัสวิชา, ชื่อวิชาภาษาไทย, ชื่อวิชาภาษาอังกฤษ, และจำนวนหน่วยกิต ส่วนอาจารย์ประกอบด้วย รหัสอาจารย์, ชื่อ-สกุล, อีเมลมหาวิทยาลัย, และสังกัดภาควิชา
- ASM-MST-06 โครงสร้างเงื่อนไขการผ่าน ประกอบด้วยเกณฑ์ 3 ส่วนหลัก ได้แก่ 1) GPAX ขั้นต่ำ, 2) หน่วยกิตสะสมขั้นต่ำ, และ 3) รายวิชาบังคับที่ต้องได้เกรดผ่าน (ไม่นับเกรดที่ไม่สมบูรณ์ตาม DOM-GRADE-01 และข้อ 16)
- ASM-MST-07 เมื่อมีการแก้ไขเงื่อนไขการผ่าน คำร้องเดิมที่คำนวณผลไปแล้วจะคงผลเดิมไว้ตาม snapshot ชุดเงื่อนไข ณ วันที่คำนวณ (IF-AUDIT-01 ใน UC-16) เงื่อนไขใหม่จะมีผลกับคำร้องรอบถัดไป
- ASM-MST-08 กลุ่มอาจารย์ (Advisor Group) ใน UC-06 ใช้ข้อมูลอาจารย์ที่จัดการในฟีเจอร์นี้ และผูกกลุ่มพร้อมโควต้าตามภาคการศึกษา
- ASM-MST-09 การลบข้อมูล Master Data ใช้การทำ Soft Delete โดยเปลี่ยนสถานะเป็นยกเลิกใช้งาน (is_active = false) เพื่อคง Referential Integrity และไม่ให้กระทบคำร้องในอดีตตาม CON-MST-02
- Open Questions: ไม่มี (ทุกข้อได้รับการสรุปเป็น Assumption เรียบร้อยแล้ว)
