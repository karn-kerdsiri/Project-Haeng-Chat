# Plan: แจ้งเตือนข่าวสารในระบบ (In-System Notification)

## 1. สรุปแนวทาง

- ฟีเจอร์นี้ใช้สร้างและแสดงการแจ้งเตือนเมื่อมีการเผยแพร่ข่าวสารหรือผลการตรวจสอบตาม DR-NTF-03
- ผู้รับต้องถูกกำหนดจากสิทธิ์และความเกี่ยวข้อง โดยต้องไม่เปิดเผยข้อมูลแก่ผู้ที่ไม่มีสิทธิ์
- ระบบจะตรวจจับเหตุการณ์ สร้างการแจ้งเตือน บันทึกสถานะ และแสดงรายการผ่านเบราว์เซอร์
- เมื่อไม่มีผู้รับ ระบบจะไม่สร้างการแจ้งเตือน และเมื่อเกิดข้อผิดพลาดจะบันทึกเหตุการณ์เพื่อรองรับการแจ้งเตือนซ้ำ
- แผนนี้ยึด React และ PostgreSQL ตาม IF-TECH-01 โดยยังไม่ตัดสินใจเรื่องอีเมล การตั้งค่าการแจ้งเตือน และรายละเอียดสถานะที่ยังเป็น Open Questions
- ค่าตัวเลขด้าน Availability, Retry, ขนาดหน้าจอ และระยะเวลาแสดงการแจ้งเตือน จะใช้ค่าตามที่ทีมยืนยันภายหลังตาม ASM-NTF-01

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React | IF-TECH-01 | ใช้พัฒนาส่วนหน้าจอสำหรับแสดงการแจ้งเตือน |
| PostgreSQL | IF-TECH-01 | ใช้จัดเก็บข้อมูลการแจ้งเตือน |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | เป็นค่าเริ่มต้นของรายวิชาสำหรับพัฒนาส่วนหลังบ้าน |
| กลไกประมวลผลเหตุการณ์และ Retry | FR-NTF-01, FR-NTF-08, NFR-NTF-02 | รองรับการบันทึกเหตุการณ์ที่ล้มเหลวและลองใหม่ตามค่าที่ทีมยืนยัน โดยยังไม่กำหนดเครื่องมือเฉพาะ |
| Browser | IF-WEB-01 | ผู้ใช้เข้าถึงการแจ้งเตือนผ่านเบราว์เซอร์ ไม่ต้องติดตั้งโปรแกรมเพิ่ม |

หมายเหตุ: ยังไม่เลือกบริการหรือแพลตฟอร์มฐานข้อมูลเพิ่มเติม เนื่องจาก ASM-NTF-02 ระบุว่าทีมต้องยืนยันแนวทางให้สอดคล้องกับ SPEC-001 ก่อน โดย Supabase ใช้ PostgreSQL เป็นฐานข้อมูล จึงต้องยืนยันว่าจะใช้ PostgreSQL ผ่าน Supabase หรือจัดการ PostgreSQL โดยตรง

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ FR / Constraint |
|---|---|---|
| Notification | notification_id, recipient_user_id, content, created_at, status, source_event_type, source_event_id | FR-NTF-02, FR-NTF-03, FR-NTF-04, FR-NTF-05, FR-NTF-09, DR-NTF-01, DR-NTF-02, DR-NTF-03 |
| NotificationEventLog | event_id, event_type, processing_status, retry_count, next_retry_at, last_error | FR-NTF-01, FR-NTF-08, NFR-NTF-02 |
| Notification Deduplication Key | source_event_id, recipient_user_id | NFR-NTF-03 |

รายละเอียด:

- Notification เก็บข้อมูลผู้รับ เนื้อหา เวลาที่สร้าง และสถานะตาม DR-NTF-01 และ DR-NTF-02
- source_event_type รองรับเหตุการณ์ตาม DR-NTF-03 ได้แก่ การเผยแพร่ข่าวสารและผลการตรวจสอบ
- NotificationEventLog ใช้บันทึกเหตุการณ์ที่ประมวลผลไม่สำเร็จและข้อมูลสำหรับการลองใหม่ตาม FR-NTF-08
- การกำหนดคู่ source_event_id และ recipient_user_id ให้ไม่ซ้ำ ใช้ป้องกันการสร้างการแจ้งเตือนซ้ำตาม NFR-NTF-03
- สถานะที่ใช้ในแผนนี้จำกัดตามที่ระบุใน DR-NTF-02 ได้แก่ สร้างแล้ว แสดงแล้ว และแจ้งไม่สำเร็จ โดยยังไม่เพิ่มสถานะอ่านแล้วจนกว่าจะได้คำตอบ OQ-NTF-03
- ยังไม่กำหนด Entity สำหรับการตั้งค่าการแจ้งเตือน เพราะขอบเขตและวิธีจัดการยังรอคำตอบ OQ-NTF-02

## 4. API / หน้าจอ

| รายการ | รายละเอียด | รองรับ FR |
|---|---|---|
| Internal Event Handler | รับเหตุการณ์เมื่อมีการเผยแพร่ข่าวสารหรือผลการตรวจสอบ เพื่อนำเข้าสู่กระบวนการแจ้งเตือน | FR-NTF-01 |
| Recipient Determination Service | ตรวจสอบสิทธิ์และความเกี่ยวข้องเพื่อกำหนดผู้รับ | FR-NTF-02 |
| Notification Creation Service | สร้างรายการแจ้งเตือนพร้อมผู้รับ เนื้อหา เวลาที่สร้าง และสถานะ | FR-NTF-03 |
| GET /notifications | ดึงรายการแจ้งเตือนของผู้ใช้ที่เข้าสู่ระบบอยู่เท่านั้น | FR-NTF-04, FR-NTF-10 |
| GET /notifications/{id} | ดึงรายละเอียดการแจ้งเตือน โดยตรวจสอบว่าเป็นผู้รับที่มีสิทธิ์เข้าถึง | FR-NTF-04, FR-NTF-10 |
| Notification Display | หน้าจอหรือส่วนแสดงรายการแจ้งเตือนบนเบราว์เซอร์ รองรับการแสดงผลบนมือถือ | FR-NTF-04, IF-WEB-01, NFR-NTF-05, NFR-NTF-06 |
| Notification Status Service | บันทึกสถานะการสร้างและการแสดงการแจ้งเตือน | FR-NTF-05 |
| Retry Handler | บันทึกเหตุการณ์ที่แจ้งเตือนไม่สำเร็จ และดำเนินการลองใหม่เมื่อระบบพร้อมตามค่าที่ทีมยืนยัน | FR-NTF-08, NFR-NTF-02 |
| Authorization Middleware | ตรวจสอบตัวตนและสิทธิ์ก่อนเข้าถึงข้อมูลการแจ้งเตือน พร้อมปฏิเสธการเรียกข้ามผู้ใช้ | IF-AUTH-01, FR-NTF-10, CON-NTF-01, CON-NTF-02 |

หมายเหตุ:

- Internal Event Handler เป็นแนวทางเชื่อมต่อภายในระบบ ไม่ได้กำหนดวิธีเรียกหรือรูปแบบ payload เพิ่มเติมแทนทีม
- หากไม่มีผู้รับที่เกี่ยวข้อง ต้องจบกระบวนการโดยไม่สร้าง Notification ตาม FR-NTF-06 และ CON-NTF-03
- ยังไม่สร้าง API หรือหน้าจอสำหรับตั้งค่าการแจ้งเตือน เนื่องจากอยู่นอกขอบเขตที่ยืนยันแล้วตาม OUT-NTF-05 และ OQ-NTF-02
- ไม่มี API สำหรับส่งอีเมลหรือข้อความภายนอก เพราะอยู่นอกขอบเขตตาม OUT-NTF-03 และ OQ-NTF-01

| IF-WEB-01 | แสดงการแจ้งเตือนผ่าน Browser โดยไม่ต้องติดตั้งโปรแกรมเพิ่ม | ใช้แล้ว |

| CON-NTF-02 | ตรวจสอบเนื้อหาก่อนสร้างและแสดงการแจ้งเตือน เพื่อไม่เปิดเผยข้อมูลแก่ผู้ไม่มีสิทธิ์ | ใช้แล้ว |
| CON-NTF-03 | หากไม่มีผู้รับที่เกี่ยวข้อง จะไม่สร้างรายการ Notification | ใช้แล้ว |

- AC-NTF-03 และ AC-NTF-08 ต้องใช้ค่าจำนวนครั้ง ระยะเวลา Retry และเกณฑ์เวลาแสดงการแจ้งเตือนที่ทีมยืนยันแล้ว ไม่กำหนดตัวเลขเพิ่มเติมเอง
- AC-NTF-07 ยังขึ้นกับขอบเขตการตั้งค่าที่ทีมสรุปจาก OQ-NTF-02

## 7. ลำดับงาน

1. ออกแบบโครงสร้างข้อมูล Notification และข้อมูลอ้างอิงเหตุการณ์ให้รองรับผู้รับ เนื้อหา เวลาที่สร้าง และสถานะตาม DR-NTF-01 ถึง DR-NTF-03 (รองรับ FR-NTF-03, FR-NTF-05)
2. สร้างกระบวนการตรวจจับเหตุการณ์จากการเผยแพร่ข่าวสารหรือผลการตรวจสอบตาม DR-NTF-03 (รองรับ FR-NTF-01)
3. สร้างกระบวนการกำหนดผู้รับโดยตรวจสอบสิทธิ์และความเกี่ยวข้องก่อนสร้างการแจ้งเตือน (รองรับ FR-NTF-02, CON-NTF-01)
4. สร้างกระบวนการสร้าง Notification และป้องกันการสร้างรายการซ้ำสำหรับเหตุการณ์เดียวกันและผู้รับคนเดิม (รองรับ FR-NTF-03, NFR-NTF-03)
5. สร้าง API และส่วนหน้าจอสำหรับแสดงรายการแจ้งเตือน โดยตรวจสอบตัวตนและสิทธิ์การเข้าถึงทุกครั้ง (รองรับ FR-NTF-04, FR-NTF-10, IF-AUTH-01, IF-WEB-01)
6. เพิ่มการตรวจสอบเนื้อหาการแจ้งเตือนเพื่อป้องกันการเปิดเผยข้อมูลที่ผู้รับไม่มีสิทธิ์เห็น (รองรับ FR-NTF-09, CON-NTF-02)
7. เพิ่มการบันทึกสถานะและจัดการกรณีไม่มีผู้รับ โดยไม่สร้าง Notification เมื่อไม่มีผู้รับที่เกี่ยวข้อง (รองรับ FR-NTF-05, FR-NTF-06, CON-NTF-03)
8. สร้างกลไกบันทึกเหตุการณ์ที่ล้มเหลวและลองใหม่ตามจำนวนครั้งและระยะเวลาที่ทีมยืนยัน พร้อมป้องกันรายการซ้ำ (รองรับ FR-NTF-08, NFR-NTF-02, NFR-NTF-03)
9. ทดสอบ Acceptance Criteria ทั้ง 11 ข้อ รวมถึงการแสดงผลภาษาไทย การแสดงผลบนมือถือ และการหมดเวลาใช้งาน พร้อมทดสอบ Availability ตามค่าและวิธีวัดที่ทีมยืนยัน (รองรับ NFR-NTF-01 ถึง NFR-NTF-07 และ AC-NTF-01 ถึง AC-NTF-11)

## 8. สิ่งที่ยังไม่ทำ

- ASM-NTF-01 UC-17 ระบุ NFR เป็นหมวด (Availability, Reliability, Security) ค่าตัวเลขใน NFR-NTF-01, NFR-NTF-02, NFR-NTF-06 และ NFR-NTF-07 จึงเป็นค่าที่เสนอไว้เพื่อให้ทดสอบได้ รอทีมยืนยัน ได้แก่ ค่า Availability 99% ต่อเดือน ระยะเวลา Retry ภายใน 5 นาที จำนวน Retry สูงสุด 3 ครั้ง ความกว้างหน้าจอ 360 px และระยะเวลาแสดงการแจ้งเตือนภายใน 1 นาที รวมถึงความหมายของจำนวน 3 ครั้งและวิธีวัด Availability
- ASM-NTF-02 ข้อ 19 ระบุ React + PostgreSQL ส่วน SPEC-001 มีการใช้ Supabase ซึ่งใช้ PostgreSQL เป็นฐานข้อมูล ทีมต้องยืนยันว่าจะใช้ PostgreSQL ผ่าน Supabase หรือจัดการ PostgreSQL โดยตรง และปรับเอกสารที่เกี่ยวข้องให้สอดคล้องกัน
- OQ-NTF-01 UC-17 ระบุขอบเขตเป็นการแจ้งเตือนภายในระบบ แต่ SPEC-001 (FR-EDU-09 และ FR-EDU-10) มีข้อกำหนดเกี่ยวกับการส่งอีเมล ทีมต้องยืนยันว่าอีเมลเป็นความรับผิดชอบของ UC-17 หรือ Use Case อื่น และ UC-17 ต้องรองรับการส่งอีเมลเพิ่มเติมหรือไม่
- OQ-NTF-02 UC-17 alt 2 ระบุว่าผู้ใช้สามารถปิดการแจ้งเตือนได้ แต่ไม่มี Use Case สำหรับตั้งค่าการแจ้งเตือน ทีมต้องยืนยันว่าผู้ใช้สามารถเปิด/ปิดการแจ้งเตือนเองได้หรือไม่ หากรองรับ ต้องตั้งค่าผ่านหน้าใด และการปิดแจ้งเตือนมีผลกับการแจ้งเตือนทุกประเภทหรือเฉพาะบางประเภท
- OQ-NTF-03 ทีมต้องยืนยันรายการสถานะการแจ้งเตือนที่ระบบต้องจัดเก็บและแสดง ได้แก่ สร้างแล้ว (Created), แสดงแล้ว (Displayed), อ่านแล้ว (Read) และแจ้งไม่สำเร็จ (Failed) รวมถึงต้องยืนยันว่า “แสดงแล้ว” กับ “อ่านแล้ว” เป็นคนละสถานะหรือไม่ และระบบต้องเปลี่ยนสถานะเป็น “อ่านแล้ว” เมื่อผู้ใช้เปิดดูการแจ้งเตือนหรือไม่
- OQ-NTF-04 ทีมต้องยืนยันว่านอกจากการเผยแพร่ผลตาม UC-14 แล้ว ต้องรองรับเหตุการณ์อื่นเพิ่มเติมหรือไม่ เช่น การส่งกลับให้แก้ไขตาม UC-09 (Q-03 ใน SPEC-APR-009), การยืนยันสมาชิกกลุ่มตาม UC-08 (Q-04 ใน SPEC-GRP-008) และการเปลี่ยนตารางเวลาตาม UC-15 (OQ-SCH-05 ใน SPEC-SCH-015)
- OQ-NTF-05 ทีมต้องยืนยันนโยบายการเก็บรักษาการแจ้งเตือนว่าแจ้งเตือนจะถูกเก็บไว้นานเท่าใด มีการลบหรือหมดอายุอัตโนมัติหรือไม่ และผู้ใช้สามารถลบการแจ้งเตือนของตนเองได้หรือไม่ หากลบได้ ต้องเป็นการลบเฉพาะรายการที่แสดงต่อผู้ใช้หรือเป็นการลบข้อมูลออกจากระบบด้วย
- OQ-NTF-06 ทีมต้องยืนยันว่าระบบต้องแสดงจำนวนการแจ้งเตือนที่ยังไม่อ่าน (Unread Count) หรือไม่ หากต้องแสดง ต้องนับเฉพาะการแจ้งเตือนที่ยังไม่อ่านของผู้ใช้ที่เข้าสู่ระบบ และจำนวนดังกล่าวต้องปรับปรุงเมื่อผู้ใช้อ่านหรือลบการแจ้งเตือนหรือไม่
