# Technical Plan: เลือกกลุ่มอาจารย์ที่ปรึกษา

Spec ID: SPEC-ADV-006

อ้างอิง: [spec.md](./spec.md) Draft v2

สถานะ: ร่างเพื่อให้ทีมตรวจ

## 1. สรุปแนวทาง

- ให้นักศึกษาเรียกดูรายการกลุ่มอาจารย์ที่เปิดรับจากข้อมูลที่เจ้าหน้าที่จัดการไว้ (FR-ADV-01, IF-MST-01)
- ให้นักศึกษาเลือกหนึ่งกลุ่มต่อคำขอและดูรายละเอียดก่อนยืนยัน (FR-ADV-02/03, DR-ADV-04)
- บันทึกตัวเลือกผูกกับคำขอและภาคการศึกษาของนักศึกษา และแสดงตัวเลือกเดิมเมื่อกลับมา (FR-ADV-04/09, CON-ADV-01)
- ป้องกันการเลือกเกินโควต้าที่นับจากการอนุมัติ; การประสาน UC-09 ยังรอคำตอบ Q-ADV-03 (FR-ADV-07, DOM-QUOTA-01)
- รองรับ session บัญชีมหาวิทยาลัย หน้าจอเว็บ และกรณีผิดพลาดตาม spec; ประเด็นที่ยังไม่ยืนยันคงเป็น Q-ADV (IF-AUTH-01, IF-WEB-01, FR-ADV-05/06/08)

## 3. โมเดลข้อมูล

เป็นโมเดลเชิงแนวคิด ไม่ได้กำหนดชื่อตารางหรือ schema ในฐานข้อมูล

| Entity / ข้อมูลเชิงตรรกะ | ฟิลด์หรือข้อมูลหลัก | รองรับ |
|---|---|---|
| กลุ่มอาจารย์จากข้อมูลเจ้าหน้าที่ | ชื่อกลุ่ม, รายละเอียด, สถานะเปิดรับ, อาจารย์ที่สัมพันธ์, ข้อมูลโควต้าจากแหล่งจัดการ; ฟิลด์รายละเอียดเพิ่มเติมรอ Q-ADV-01 | FR-ADV-01/03/07, DR-ADV-01/02, IF-MST-01, DOM-QUOTA-01 |
| ตัวเลือกกลุ่มในคำขอ | คำขอ, นักศึกษา, ภาคการศึกษา, กลุ่มที่เลือก; ต้องผูกกับคำขอและไม่อนุญาตให้แก้คำขอผู้อื่น | FR-ADV-02/04/08/09, DR-ADV-03/04, CON-ADV-01, NFR-ADV-02 |
| จำนวนการอนุมัติของอาจารย์ในภาคการศึกษา | จำนวนที่ใช้เทียบกับโควต้าจากข้อมูลการอนุมัติ; แหล่งข้อมูลและจุดเชื่อมต่อกับ UC-09 รอ Q-ADV-03 | FR-ADV-07, NFR-ADV-05, DOM-QUOTA-01 |
| Session ผู้ใช้ | สถานะ session ที่ยืนยันตัวตนด้วยบัญชีมหาวิทยาลัย | IF-AUTH-01, NFR-ADV-01 |

ไม่มีการสร้างหรือแก้ไขข้อมูลกลุ่ม/อาจารย์/โควต้าในฟีเจอร์นี้ (OUT-ADV-01, IF-MST-01)

## 4. API / หน้าจอ

Path ด้านล่างเป็นข้อเสนอเพื่ออธิบายขอบเขตงาน ไม่ใช่ข้อกำหนดใน spec; รูปแบบสุดท้ายให้ทีมเลือกเอง

| รายการ | Method / path หรือหน้าจอ | Input / Output หลัก | รองรับ |
|---|---|---|---|
| อ่านรายการกลุ่ม | `GET /api/advisor-groups` (ข้อเสนอ) | Input: session; Output: กลุ่มที่เปิดรับพร้อมชื่อและรายละเอียด; การแสดงกลุ่มที่โควต้าเต็มรอ Q-ADV-02 | FR-ADV-01/05/07, DR-ADV-01/02, IF-MST-01 |
| อ่านกลุ่มที่เลือกในคำขอ | `GET /api/requests/{requestId}/advisor-group` (ข้อเสนอ) | Input: session และคำขอ; Output: กลุ่มที่เลือกไว้เดิม; คำขอของผู้อื่นต้องตอบ HTTP 403 | FR-ADV-09, NFR-ADV-02 |
| ยืนยันกลุ่มในคำขอ | `PUT /api/requests/{requestId}/advisor-group` (ข้อเสนอ) | Input: session และกลุ่มที่เลือก; Output: ผลการบันทึกที่ผูกกับคำขอ; ไม่เลือกต้องแจ้งให้เลือกและไม่บันทึก; ข้อผิดพลาดต้องไม่บันทึกบางส่วน | FR-ADV-04/06/08, DR-ADV-03, CON-ADV-01 |
| หน้ารายการและเลือกกลุ่ม | หน้าจอเว็บของนักศึกษา | แสดงกลุ่มที่เปิดรับ เลือกหนึ่งกลุ่ม และแสดงรายละเอียดก่อนยืนยัน | FR-ADV-01/02/03, IF-WEB-01 |
| สถานะว่าง/ข้อผิดพลาด | ข้อความภาษาไทยในหน้าจอ | ไม่มีกลุ่มให้เลือก, ยังไม่ได้เลือก, หรือบันทึกผิดพลาด; ระบุช่องที่ต้องแก้ตามกรณี | FR-ADV-05/06/08, NFR-ADV-03 |

ทุก request ต้องตรวจ session และตอบ HTTP 401 หากไม่ผ่านการยืนยันตัวตน (IF-AUTH-01); session ต้องหมดอายุหลังไม่มีการใช้งานต่อเนื่องเกิน 30 นาที (NFR-ADV-01)

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| IF-AUTH-01 | ตรวจ session บัญชีมหาวิทยาลัยในทุก request; ไม่มี session ที่ยืนยันตัวตนตอบ HTTP 401 | ใช้แล้ว |
| IF-WEB-01 | หน้ารายการ เลือกกลุ่ม และรายละเอียดทำงานบนเบราว์เซอร์โดยไม่ต้องติดตั้งโปรแกรม | ใช้แล้ว |
| IF-TECH-01 | React สำหรับหน้าจอและ PostgreSQL สำหรับข้อมูลกลุ่ม; วิธีเชื่อมต่อแหล่งข้อมูลรอทีมเลือก | ใช้แล้ว |
| IF-MST-01 | อ่านกลุ่มและโควต้าจากข้อมูลที่เจ้าหน้าที่จัดการ โดยไม่สร้างข้อมูลซ้ำ | ใช้แล้ว |
| DOM-QUOTA-01 | เปรียบเทียบการอนุมัติต่ออาจารย์/ภาคการศึกษากับโควต้า; จุดเชื่อม UC-09 รอ Q-ADV-03 | ใช้แล้ว |
| CON-ADV-01 | บันทึกกลุ่มที่เลือกผูกกับคำขอของนักศึกษาคนนั้นในภาคการศึกษานั้น | ใช้แล้ว |

## 7. ลำดับงาน

1. ตรวจ source ข้อมูลกลุ่ม/โควต้าที่เจ้าหน้าที่จัดการและความสัมพันธ์กับคำขอ/ภาคการศึกษา (FR-ADV-01, IF-MST-01, CON-ADV-01)
2. สร้างการอ่านรายการกลุ่มเปิดรับและแสดงชื่อ/รายละเอียดที่ยืนยันแล้ว (FR-ADV-01, DR-ADV-01/02)
3. สร้างการเลือกหนึ่งกลุ่มและแสดงรายละเอียดก่อนยืนยัน (FR-ADV-02/03, DR-ADV-04)
4. เพิ่มการตรวจว่ามีการเลือกและบันทึกกับคำขอโดยป้องกันการแก้ไขคำขอของผู้อื่น (FR-ADV-04/06, NFR-ADV-02, CON-ADV-01)
5. โหลดตัวเลือกเดิมและจัดการข้อผิดพลาดโดยไม่บันทึกบางส่วน (FR-ADV-08/09)
6. เชื่อมข้อมูลโควต้ากับการอนุมัติและทดสอบกรณีพร้อมกันหลังได้คำตอบ Q-ADV-03 (FR-ADV-07, NFR-ADV-05, AC-ADV-04/05)
7. ทำหน้าจอเว็บและข้อความผิดพลาดภาษาไทย พร้อมตรวจ session timeout และการใช้งานบนมือถือ (IF-WEB-01, IF-AUTH-01, NFR-ADV-01/03/04)
8. รันการตรวจสอบตาม AC-ADV-01 ถึง AC-ADV-08 และ NFR ที่เกี่ยวข้อง; เกณฑ์ตัวเลขรอ Q-ADV-06

## 8. สิ่งที่ยังไม่ทำ

รหัส Q-ADV ในแผนนี้ใช้ติดตามคำถามเท่านั้น ไม่ได้เพิ่ม requirement ID ใน spec; ทุกข้อด้านล่างรอคำตอบจากทีม และส่วนที่เกี่ยวข้องจะยังไม่สร้างจนกว่าจะได้คำตอบ

- **Q-ADV-01 (DR-ADV-01):** ต้องแสดงฟิลด์ใดนอกจากชื่อกลุ่มและรายละเอียด? หมายเหตุ: DR-ADV-01 อ้างถึง OQ-ADV-01 แต่ในรายการ Open Questions ของ spec v2 ไม่มี OQ-ADV-01
- **Q-ADV-02 (FR-ADV-07):** กลุ่มที่โควต้าการอนุมัติเต็มแล้วควรถูกซ่อนจากรายการหรือแสดงแต่เลือกไม่ได้?
- **Q-ADV-03 (FR-ADV-07, NFR-ADV-05, AC-ADV-05, OUT-ADV-03):** การบังคับโควต้าในการอนุมัติพร้อมกันเป็นความรับผิดชอบและจุดเชื่อมต่อของ UC-09 อย่างไร เมื่อการอนุมัติอยู่นอกขอบเขต UC-06 และ NFR-ADV-05 กล่าวถึงทั้งการอนุมัติและการบันทึกการเลือก?
- **Q-ADV-04 (OQ-ADV-04):** นักศึกษาเปลี่ยนกลุ่มที่เลือกได้จนถึงเมื่อใด และถ้าอาจารย์อนุมัติแล้วยังเปลี่ยนได้หรือไม่?
- **Q-ADV-05 (OQ-ADV-05):** กรณีทำงานแบบกลุ่ม/คู่ตาม UC-08 สมาชิกทุกคนต้องอยู่กลุ่มอาจารย์เดียวกันหรือไม่?
- **Q-ADV-06 (ASM-ADV-01):** ทีมยืนยันค่าที่เสนอไว้ใน NFR-ADV-04 (360 px) และ NFR-ADV-06 (p95 <= 2 วินาที) หรือไม่?
- **Q-ADV-07 (ASM-ADV-02):** ทีมจะจัดการความต่างระหว่าง React/PostgreSQL ใน spec นี้กับ Supabase ใน plan ของ specs/001 อย่างไร?
