# Technical Plan: เลือกกลุ่มอาจารย์ที่ปรึกษา

Spec ID: SPEC-ADV-006

อ้างอิง: [spec.md](./spec.md) Draft v2

สถานะ: รอคำตอบ Q-xx ที่กระทบการออกแบบ/ทดสอบ

## 1. เป้าหมายและขอบเขต

วางแนวทางพัฒนาการแสดงกลุ่มอาจารย์ที่เปิดรับ ให้นักศึกษาเลือกหนึ่งกลุ่ม ดูรายละเอียด ยืนยันและบันทึกกลุ่มไว้กับคำขอส่งผลการศึกษา และกลับมาเห็นตัวเลือกเดิมได้ ตาม IN-ADV-01 ถึง IN-ADV-05

ไม่รวมการจัดการข้อมูลอาจารย์/กลุ่ม/โควต้า (OUT-ADV-01), การกรอกหรือส่งผลการศึกษา (OUT-ADV-02), การอนุมัติ (OUT-ADV-03), การจัดการสมาชิกกลุ่ม/คู่ (OUT-ADV-04) และการจัดสรรอัตโนมัติ (OUT-ADV-05)

## 2. ข้อกำหนดและข้อจำกัดทางเทคนิค

- หน้าจอใช้ React และข้อมูลกลุ่มอาจารย์เก็บใน PostgreSQL (IF-TECH-01)
- อ่านรายการกลุ่มและโควต้าจากข้อมูลที่เจ้าหน้าที่จัดการ ห้ามสร้างข้อมูลซ้ำในฟีเจอร์นี้ (IF-MST-01)
- ทุก request ต้องมี session ที่ยืนยันตัวตนด้วยบัญชีของมหาวิทยาลัย มิฉะนั้นตอบ HTTP 401 (IF-AUTH-01)
- กลุ่มหนึ่งสัมพันธ์กับอาจารย์หนึ่งคน; นักศึกษาหนึ่งคนเลือกหนึ่งกลุ่มต่อหนึ่งคำขอ; โควต้านับเมื่ออาจารย์อนุมัติ ตาม ASM-ADV-04 ถึง ASM-ADV-06
- เทคโนโลยีอื่นนอกเหนือจากที่ระบุข้างต้น เช่น backend framework, รูปแบบ API, กลไก session, schema/migration และ test framework: ทีมเลือกเอง ไม่ได้มาจาก spec

## 3. แนวทางองค์ประกอบงาน

### 3.1 อ่านและแสดงรายการกลุ่ม

- อ่านข้อมูลจากแหล่งข้อมูลที่เจ้าหน้าที่จัดการ และแสดงกลุ่มที่เปิดรับพร้อมชื่อและรายละเอียดตาม DR-ADV-01/02 และ FR-ADV-01
- กลุ่มที่โควต้าการอนุมัติเต็มแล้วต้องเลือกไม่ได้ตาม FR-ADV-07; รูปแบบการแสดงกลุ่มเต็มยังรอ Q-02
- กรณีไม่มีรายการที่เลือกได้ แจ้งว่าไม่สามารถเลือกได้และปิดกั้นการยืนยันตาม FR-ADV-05
- รายละเอียดเพิ่มเติมที่ต้องแสดงยังรอ Q-01

### 3.2 เลือกและแสดงรายละเอียด

- ให้นักศึกษาเลือกได้หนึ่งกลุ่มต่อคำขอ ตาม DR-ADV-04 และ FR-ADV-02
- แสดงรายละเอียดของกลุ่มที่เลือกก่อนยืนยัน ตาม FR-ADV-03
- ยังไม่ได้เลือกกลุ่มต้องแจ้งให้เลือกและไม่บันทึก ตาม DR-ADV-03 และ FR-ADV-06

### 3.3 ยืนยัน บันทึก และโหลดค่าที่บันทึกไว้

- ผูกค่าที่เลือกกับคำขอส่งผลการศึกษาของนักศึกษาคนนั้นและภาคการศึกษานั้น ตาม CON-ADV-01 และ FR-ADV-04
- ป้องกันการแก้ไขข้อมูลของคำขอที่เป็นของนักศึกษาคนอื่น โดยตอบ HTTP 403 และไม่เปลี่ยนข้อมูล ตาม NFR-ADV-02
- เมื่อกลับเข้าขั้นตอน ให้โหลดกลุ่มที่บันทึกไว้ ตาม FR-ADV-09
- หากบันทึกผิดพลาด ต้องไม่มีข้อมูลบางส่วนถูกบันทึกและต้องแจ้งข้อผิดพลาด ตาม FR-ADV-08
- ข้อความผิดพลาดเป็นภาษาไทยและระบุช่องที่ต้องแก้ ตาม NFR-ADV-03

### 3.4 Session และหน้าจอ

- ตรวจ session สำหรับทุก request; session หมดอายุหรือไม่มีการยืนยันตัวตนตอบ HTTP 401 ตาม IF-AUTH-01
- รองรับการตัด session เมื่อไม่มีการใช้งานต่อเนื่องเกิน 30 นาที ตาม NFR-ADV-01
- ออกแบบหน้าจอให้ใช้งานบนเบราว์เซอร์โดยไม่ติดตั้งโปรแกรมเพิ่ม (IF-WEB-01)
- ทดสอบการไม่เกิด horizontal scroll ที่ความกว้าง 360 px ตามค่าเสนอใน NFR-ADV-04; ค่าดังกล่าวยังรอการยืนยันตาม Q-07

## 4. ข้อมูลและความถูกต้อง

- ข้อมูลกลุ่มและโควต้าเป็นข้อมูลอ้างอิงจากแหล่งจัดการเดิม ไม่สร้างสำเนาในฟีเจอร์ (IF-MST-01)
- ข้อมูลการเลือกต้องอ้างถึงคำขอและภาคการศึกษาตาม CON-ADV-01; รายละเอียด schema ไม่ได้ระบุใน spec และให้ทีมเลือก
- โควต้าต่ออาจารย์ต่อภาคการศึกษาเป็นไปตาม DOM-QUOTA-01 โดยนับการอนุมัติแล้วตาม ASM-ADV-06
- ต้องรักษาเงื่อนไขไม่ให้เกินโควต้าแม้มีการอนุมัติพร้อมกัน ตาม NFR-ADV-05/AC-ADV-05 อย่างไรก็ตาม การอนุมัติเป็น OUT-ADV-03 และจุดเชื่อมต่อกับ UC-09 ยังต้องยืนยันตาม Q-03
- วิธีทำให้การบันทึกเป็นแบบ all-or-nothing ตาม FR-ADV-08 เป็นรายละเอียดทางเทคนิคที่ทีมเลือก ไม่ได้มาจาก spec

## 5. แผนตรวจสอบและเกณฑ์ทดสอบ

เพิ่มการทดสอบที่ผูกกับ AC เดิม โดยไม่สร้าง ID ข้อกำหนดใหม่:

| AC | การตรวจสอบ |
|---|---|
| AC-ADV-01 | เลือกกลุ่มและยืนยันแล้วผูกกลุ่มกับคำขอของนักศึกษาคนนั้น |
| AC-ADV-02 | ไม่มีรายการกลุ่มเปิดรับ: แสดงข้อความและยืนยันไม่ได้ |
| AC-ADV-03 | ยืนยันโดยไม่เลือก: แจ้งให้เลือกและไม่มีการบันทึก |
| AC-ADV-04 | กลุ่มที่จำนวนการอนุมัติถึงโควต้าแล้วเลือกไม่ได้ |
| AC-ADV-05 | การอนุมัติพร้อมกันในโควต้าที่เหลือหนึ่งที่นั่งต้องไม่ทำให้เกินโควต้า |
| AC-ADV-06 | ฐานข้อมูลไม่พร้อมระหว่างบันทึก: ไม่มีข้อมูลบางส่วนและแจ้งข้อผิดพลาด |
| AC-ADV-07 | กลับเข้าขั้นตอนแล้วแสดงกลุ่มที่เลือกไว้ |
| AC-ADV-08 | นักศึกษาแก้คำขอของผู้อื่นไม่ได้: HTTP 403 และข้อมูลไม่เปลี่ยน |

ทดสอบ NFR-ADV-01 ถึง NFR-ADV-06 เพิ่มเติม: session inactivity, ภาษา/ช่องของข้อความผิดพลาด, การแสดงผลบนมือถือ และ p95 ของการบันทึกไม่เกิน 2 วินาที โดยค่า 360 px และ 2 วินาทียังคงเป็นค่าที่เสนอไว้ตาม ASM-ADV-01 จนกว่าจะได้รับการยืนยัน

## 6. ลำดับการพัฒนา

1. ยืนยัน Q-01 ถึง Q-07 ที่มีผลต่อฟิลด์แสดงผล การกรองกลุ่มเต็ม การเชื่อม UC-09 การเปลี่ยนกลุ่ม เงื่อนไขกลุ่ม/คู่ และเกณฑ์ตัวเลข
2. ออกแบบการอ่านข้อมูลกลุ่ม/โควต้าจากแหล่งที่เจ้าหน้าที่จัดการ และการเชื่อมข้อมูลการเลือกกับคำขอ (FR-ADV-01, CON-ADV-01)
3. พัฒนารายการกลุ่ม การเลือก และรายละเอียดก่อนยืนยัน (FR-ADV-02/03/05/06)
4. พัฒนาการยืนยัน บันทึก การตรวจสิทธิ์ และการโหลดค่าที่เลือกไว้ (FR-ADV-04/08/09, NFR-ADV-02)
5. ตรวจโควต้าและประสานจุดเชื่อมการอนุมัติตามคำตอบ Q-03 (FR-ADV-07, NFR-ADV-05)
6. ตรวจ AC-ADV-01 ถึง AC-ADV-08 และ NFR ที่เกี่ยวข้อง

## 7. คำถามที่รอคำตอบจากทีม

- **Q-01 (DR-ADV-01):** นอกจากชื่อกลุ่มและรายละเอียด ต้องแสดงฟิลด์ใดบ้าง เช่น หัวข้อที่รับหรือจำนวนที่ว่าง? หมายเหตุ: DR-ADV-01 อ้างถึง OQ-ADV-01 แต่ในรายการคำถามของ spec v2 ไม่มีรายการดังกล่าว
- **Q-02 (FR-ADV-07):** กลุ่มที่โควต้าการอนุมัติเต็มแล้วควรถูกซ่อนจากรายการ หรือแสดงแต่เลือกไม่ได้?
- **Q-03 (FR-ADV-07, NFR-ADV-05, AC-ADV-05 / OUT-ADV-03):** การบังคับโควต้าในช่วงอนุมัติพร้อมกันเป็นความรับผิดชอบและจุดเชื่อมต่อของ UC-09 อย่างไร เมื่อการอนุมัติอยู่นอกขอบเขต UC-06?
- **Q-04 (NFR-ADV-05, ASM-ADV-06):** ข้อความ “การอนุมัติหรือบันทึกการเลือกกลุ่ม” ใน NFR-ADV-05 ต้องบังคับใช้โควต้าเมื่อบันทึกการเลือกด้วยหรือไม่ เมื่อ ASM-ADV-06 ระบุว่าโควต้านับเมื่ออาจารย์อนุมัติ?
- **Q-05 (OQ-ADV-04):** นักศึกษาเปลี่ยนกลุ่มที่เลือกได้ถึงเมื่อใด และเปลี่ยนได้หรือไม่หลังอาจารย์อนุมัติแล้ว?
- **Q-06 (OQ-ADV-05):** กรณีทำงานเป็นกลุ่ม/คู่ สมาชิกทุกคนต้องอยู่กลุ่มอาจารย์เดียวกันหรือไม่?
- **Q-07 (NFR-ADV-04, NFR-ADV-06 / ASM-ADV-01):** ทีมยืนยันค่าที่เสนอไว้คือ 360 px สำหรับหน้าจอมือถือ และ p95 ไม่เกิน 2 วินาทีหรือไม่?

## 8. Traceability

การพัฒนาและการทดสอบต้องอ้างอิง ID ที่มีอยู่ใน spec เท่านั้น: IN-ADV-01 ถึง IN-ADV-05, OUT-ADV-01 ถึง OUT-ADV-05, IF-AUTH-01, IF-WEB-01, IF-TECH-01, IF-MST-01, DOM-QUOTA-01, CON-ADV-01, DR-ADV-01 ถึง DR-ADV-04, FR-ADV-01 ถึง FR-ADV-09, NFR-ADV-01 ถึง NFR-ADV-06 และ AC-ADV-01 ถึง AC-ADV-08
