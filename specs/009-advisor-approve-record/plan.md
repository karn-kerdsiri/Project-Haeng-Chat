# Plan: SPEC-APR-009 ตรวจสอบและอนุมัติผลการศึกษาของนักศึกษา

## 1. สรุปแนวทาง (5 บรรทัด)

- ให้อาจารย์ดูรายการนักศึกษาที่อยู่ในความดูแลและรอตรวจสอบ โดยแสดงชื่อ รหัส และสถานะตาม FR-APR-01 และ DR-APR-01
- ให้เลือกนักศึกษาหนึ่งคนต่อครั้งเพื่อดูผลการศึกษากับข้อมูลคำร้อง โดยขอบเขตข้อมูลรายละเอียดรอ Q-01 ตาม FR-APR-02 และ DR-APR-02
- ให้ตัดสินใจอนุมัติหรือส่งกลับทีละคน; กรณีส่งกลับต้องกรอกเหตุผลข้อความก่อน ตาม FR-APR-03 ถึง FR-APR-05 และ ASM-APR-04/05
- บันทึกสถานะและประวัติผู้ดำเนินการ พร้อมจำกัดสิทธิ์ตามผู้ดูแล และคงสถานะเดิมเมื่อบันทึกไม่สำเร็จ ตาม FR-APR-07/08, IF-AUDIT-01 และ CON-APR-01/02
- แสดงสถานะล่าสุดแก่นักศึกษาผ่าน UC-03 และส่งต่อไป UC-11 หลังอนุมัติ โดยไม่สร้างรายละเอียดของสอง use case นั้น ตาม FR-APR-09/10 และ OUT-APR-01

## 4. API / หน้าจอ

ชื่อ path เป็นข้อเสนอทางเทคนิคสำหรับแผน ไม่ใช่ requirement; API ทุกตัวต้องตรวจ session ตาม IF-AUTH-01 และตรวจขอบเขตผู้ดูแลตาม CON-APR-01/FR-APR-11. รายละเอียดที่ขึ้นกับ Q จะยังไม่กำหนด

| รายการ | รายละเอียด | รองรับ ID ใน spec |
|---|---|---|
| `GET /api/advisor/reviews` | Input: session ของอาจารย์; Output: รายการนักศึกษาในความดูแลที่รอตรวจ พร้อมชื่อ รหัส และสถานะตาม DR-APR-01; ถ้าไม่มีรายการให้แจ้งตาม FR-APR-06 | FR-APR-01/06, DR-APR-01, CON-APR-01 |

| `POST /api/advisor/reviews/{requestId}/decision` | Input: ผลตัดสินใจหนึ่งค่า และเหตุผลข้อความเมื่อเลือกส่งกลับ; Output: ผลบันทึกและสถานะล่าสุด โดยชื่อสถานะรอ Q-02; เมื่อบันทึกไม่สำเร็จต้องคงสถานะเดิมตาม CON-APR-02 | FR-APR-03/04/05/07/08/09/11, DR-APR-03/04/05, IF-AUDIT-01, CON-APR-01/02, Q-02/05 |

| การแสดงสถานะผลและการไป UC-11 | ส่งสถานะล่าสุดไปแสดงฝั่งนักศึกษาผ่าน UC-03; หลังอนุมัติเปิดทางให้ดำเนิน UC-11 ต่อ โดยไม่ทำรายละเอียด UC-11 ในแผนนี้ | FR-APR-09/10, OUT-APR-01, Q-02 |

## 7. ลำดับงาน

1. ยืนยันสัญญาข้อมูลที่แสดงและชื่อสถานะกับผู้รับผิดชอบก่อนกำหนดฟิลด์หน้ารายละเอียด/สถานะ; ไม่ล็อกข้อมูลเหล่านี้จนกว่าจะตอบ Q-01/Q-02 (FR-APR-02/04/05/09, DR-APR-02).
2. เชื่อมรายการรอตรวจสอบกับข้อมูลอาจารย์และนักศึกษาที่มีอยู่ โดยจำกัด scope ตามผู้ดูแล และรองรับกรณีไม่มีรายการ (FR-APR-01/06/11, DR-APR-01, CON-APR-01).
3. สร้างหน้าจอรายการและรายละเอียดบน React/Browser พร้อมการเลือกนักศึกษาทีละคน (FR-APR-01/02, IF-WEB-01, IF-TECH-01, ASM-APR-05).
4. เพิ่มการตัดสินใจอนุมัติ/ส่งกลับ; บังคับเหตุผลข้อความก่อนส่งกลับ และไม่รองรับ bulk action (FR-APR-03/04/05, DR-APR-03/04, ASM-APR-04/05).
5. บันทึกผล/สถานะและ audit history ใน PostgreSQL; รักษาสถานะเดิมเมื่อบันทึกล้มเหลว; รายละเอียด failure semantics รอ Q-05 (FR-APR-04/05/07/08, DR-APR-05, IF-TECH-01, IF-AUDIT-01, CON-APR-02).
6. เชื่อมการแสดงสถานะล่าสุดกับ UC-03 และทางไป UC-11 โดยไม่ขยายรายละเอียดของสอง use case; รอการยืนยัน state labels สำหรับการเชื่อม (FR-APR-09/10, OUT-APR-01, Q-02).
7. บังคับใช้ session/authorization และข้อความผิดพลาดให้ตรงข้อกำหนด; ออกแบบรายละเอียดการตอบเมื่อระบบบัญชี/ประวัติไม่พร้อมหลังได้คำตอบ Q-05 (IF-AUTH-01, FR-APR-07/11, NFR-APR-02/04, CON-APR-01/02, Q-05).
8. รันการทดสอบ AC-APR-01 ถึง AC-APR-08; ทดสอบ NFR/401 ที่ไม่มี AC โดยตรงต่อเมื่อทีมปรับ AC เดิมหรือให้แนวทางตาม Q-07 และยืนยันค่าตาม Q-06 (AC-APR-01–08, NFR-APR-01/03/04/05/06, Q-06/07).

## 8. สิ่งที่ยังไม่ทำ

- Q-01 (เดิม OQ-APR-01) อาจารย์ต้องเห็นข้อมูลอะไรบ้างในหน้าตรวจสอบ (รายวิชาและเกรดทั้งหมด ผลการตรวจเบื้องต้นจาก UC-07 ข้อมูลสมาชิกกลุ่มจาก UC-08 หรือเอกสารแนบ); ต้องรอคำตอบจากทีมและอาจารย์ที่ปรึกษา — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-02 (เดิม OQ-APR-03) ชื่อสถานะหลังอนุมัติและหลังส่งกลับใช้คำว่าอะไร และต้องสอดคล้องกับรายการสถานะใน OQ-OWN-01 ของ specs/003 อย่างไร; ต้องรอคำตอบจากทีม ผู้รับผิดชอบ UC-03 และอาจารย์ผู้ตรวจสอบ — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-03 (เดิม OQ-APR-04) เมื่ออาจารย์ส่งกลับให้แก้ไข ต้องแจ้งเตือนนักศึกษาผ่าน UC-17 หรือไม่; ต้องรอคำตอบจากทีมและผู้รับผิดชอบ UC-17 — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-04 (เดิม OQ-APR-05) เมื่อนักศึกษาส่งผลเพิ่มเติมตาม UC-02 หลังอาจารย์อนุมัติแล้ว อาจารย์ต้องอนุมัติใหม่หรือไม่; ต้องรอคำตอบจากทีม ผู้รับผิดชอบ UC-02 และอาจารย์ที่ปรึกษา — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-05 (IF-AUTH-01, IF-AUDIT-01, FR-APR-07, CON-APR-02, AC-APR-04) เมื่อระบบบัญชีมหาวิทยาลัย ฐานข้อมูล หรือการบันทึกประวัติไม่พร้อมขณะอนุมัติหรือส่งกลับ ระบบต้องแจ้งและคงสถานะ/ประวัติอย่างไร; ต้องรอคำตอบจากทีมและผู้ดูแลระบบบัญชี/ฐานข้อมูล — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
- Q-06 (ASM-APR-01, NFR-APR-03, NFR-APR-05, NFR-APR-06) ทีมยืนยันค่าระยะเก็บประวัติ 1 ปี, หน้าจอ 360 px และ p95 2 วินาทีหรือไม่; หากไม่ยืนยัน ต้องใช้ค่าใด; ต้องรอคำตอบจากทีม — ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ
